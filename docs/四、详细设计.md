# 四、详细设计

本章在系统设计基础上进一步细化 iDrug——多场景 DTI 预测与个性化药物推荐辅助平台的类结构、核心交互流程、页面 UI 组织和数据库设计。平台整体以 Django 后端为中心，前端页面通过 HTTP/JSON 与后端接口交互，后端再统一调度多模型推理环境、本地知识库、MySQL 数据库和外部公共数据源。

## 4.1 类图

### 4.1.1 关系总览

iDrug 平台后端主要由 Django 视图类、业务函数、数据模型、序列化器和模型推理服务组成。由于项目以 Web 平台和模型调度为核心，部分类以 Django `APIView` 形式存在，部分复杂逻辑以服务函数形式封装。核心类与模块关系如图 4-1 所示。

![图4-1 iDrug 核心类图](详细设计图/图4-1-iDrug核心类图.svg)

### 4.1.2 用户管理相关类

| 类或模块 | 所属文件 | 主要职责 |
|---|---|---|
| `RegisterView` | `backend/web/views.py` | 处理用户注册请求，校验用户名是否存在，调用序列化器保存用户信息。 |
| `LoginView` | `backend/web/views.py` | 处理用户登录请求，校验用户名和密码，写入当前 session。 |
| `logout_view` | `backend/web/views.py` | 清理当前用户会话，实现退出登录。 |
| `current_user_view` | `backend/web/views.py` | 返回当前登录用户信息，供前端导航栏和用户中心使用。 |
| `User` | `backend/web/ms.py` | 用户数据模型，包含用户名和密码字段。 |
| `UserModelSerializer` | `backend/web/serializer.py` | 用户注册数据的序列化与字段约束。 |

设计说明：用户管理模块为结果保存和历史记录隔离提供身份基础。当前项目采用简单账号密码模型，能够满足课程项目的注册、登录和会话识别需求。后续若用于更严格环境，应进一步加入密码哈希、权限分级、验证码和登录频率限制。

### 4.1.3 预测服务相关类与模块

| 类或模块 | 所属文件 | 主要职责 |
|---|---|---|
| `PredictionModelsRunView` | `backend/web/views.py` | 多场景模型预测入口，接收任务类型、药物输入和蛋白输入。 |
| `DTI` | `backend/web/views.py` | 传统 DTI 预测与推荐流程入口，组织药物、靶点和概率结果。 |
| `prediction_model_services` | `backend/web/prediction_model_services.py` | 负责任务—模型匹配、临时输入文件生成、独立模型脚本调用和输出解析。 |
| `run_prediction_task` | `backend/web/prediction_model_services.py` | 根据任务类型调用 HyperAttentionDTI、PSICHIC 或 DeepDTA。 |
| `predict_hyperattention_scores` | `backend/web/prediction_model_services.py` | 调用 HyperAttentionDTI 返回候选 DTI 分数。 |
| `run_psichic` | `backend/web/prediction_model_services.py` | 调用 PSICHIC 完成新药评估任务。 |
| `run_deepdta` | `backend/web/prediction_model_services.py` | 调用 DeepDTA 完成亲和力预测任务。 |

设计说明：预测服务采用“任务—模型匹配”的方式，将前端任务类型与具体模型解耦。Django 后端只暴露统一 API，具体模型路径、权重文件、临时文件和 Python 解释器由服务层处理，便于后续替换模型或新增任务类型。

### 4.1.4 个性化推荐相关模块

| 类或模块 | 所属文件 | 主要职责 |
|---|---|---|
| `personalized_recommend` | `backend/web/views.py` | 个性化推荐接口，接收用户画像、药物和靶点信息，返回重排序结果。 |
| `personalization_options` | `backend/web/views.py` | 返回疾病标签、过敏标签、医保偏好等前端选项。 |
| `personalization` | `backend/web/personalization.py` | 封装用户画像构建、药物元数据加载、风险惩罚、疾病匹配、医保偏好和重排序算法。 |
| `build_patient_profile` | `backend/web/personalization.py` | 标准化年龄、性别、疾病史、过敏史和医保偏好。 |
| `rerank_drugs` | `backend/web/personalization.py` | 根据基础预测分数和个性化因素生成综合排名。 |
| `build_recommendation_reason` | `backend/web/personalization.py` | 为推荐结果生成可读解释信息。 |
| `DiseaseRecommendation` | `backend/web/models.py` | 保存疾病相关药物推荐业务数据。 |

设计说明：个性化推荐模块在基础 DTI 分数之外引入用户画像和药物属性，使结果更接近“辅助决策”而不只是模型输出。排序逻辑应保持可解释性，推荐理由中需要说明疾病匹配、过敏风险、医保偏好等因素如何影响排名。

### 4.1.5 查询展示相关类与模块

| 类或模块 | 所属文件 | 主要职责 |
|---|---|---|
| `DrugView` | `backend/web/views.py` | 接收药物查询请求，支持 CID、SMILES 等输入方式。 |
| `ProteinView` | `backend/web/views.py` | 接收蛋白质查询请求，支持 PDB、UniProt、Sequence 等输入方式。 |
| `ComplexView` | `backend/web/views.py` | 接收复合物查询请求，返回复合物结构信息。 |
| `drug_services` | `backend/web/drug_services.py` | 封装 PubChem 查询、本地 CID-SMILES 映射和药物结构信息组织。 |
| `protein_services` | `backend/web/protein_services.py` | 封装 PDB、UniProt、本地蛋白和复合物映射查询逻辑。 |
| `PDBURL` | `backend/web/ms.py` | PDB ID 与结构资源 URL 映射表。 |
| `data_sources_summary` | `backend/web/views.py` | 返回本地结构化数据源摘要和预览信息。 |

设计说明：查询展示模块优先读取本地结构化数据和缓存，必要时再访问外部数据源。这样既能提高响应速度，也能在网络接口不稳定时保留部分可用结果。

### 4.1.6 结果管理相关函数

| 函数 | 所属文件 | 主要职责 |
|---|---|---|
| `save_recommendation_result` | `backend/web/views.py` | 保存当前用户的预测或推荐结果。 |
| `saved_recommendation_list` | `backend/web/views.py` | 返回当前用户历史记录列表和公开 demo 记录。 |
| `saved_recommendation_detail` | `backend/web/views.py` | 返回指定保存记录详情。 |
| `saved_recommendation_delete` | `backend/web/views.py` | 删除当前用户的指定历史记录。 |
| `_current_session_username` | `backend/web/views.py` | 从 session 中解析当前登录用户。 |
| `_user_saved_recommendations_dir` | `backend/web/views.py` | 定位当前用户结果保存目录。 |

设计说明：结果管理模块使系统形成完整使用闭环。用户不仅可以即时预测，还可以保存、查看和删除历史结果。公开 demo 记录用于课程演示，应在删除逻辑中与普通用户记录区分。

## 4.2 交互图

### 4.2.1 预测与个性化推荐交互图

预测与推荐流程是平台最核心的业务链路。用户在前端页面输入药物、靶点和用户画像后，前端通过 API 向 Django 后端提交请求。后端先调用模型服务生成基础 DTI 分数，再调用个性化排序服务读取疾病、过敏、医保和药物属性数据，最终生成综合排序结果和推荐理由。若用户选择保存结果，系统会将结果写入当前用户的历史记录。

![图4-2 预测与个性化推荐交互图](详细设计图/图4-2-预测与个性化推荐交互图.svg)

交互流程说明：

1. 用户在预测或推荐页面输入药物信息、靶点信息和可选用户画像。
2. 前端以 JSON 形式向后端提交请求。
3. 后端校验输入后调用模型调度服务。
4. 模型服务根据任务类型执行 HyperAttentionDTI、PSICHIC 或 DeepDTA。
5. 个性化排序服务读取本地知识库中的疾病、过敏、医保和药物属性信息。
6. 系统计算综合分数，生成排序结果、风险提示和推荐原因。
7. 前端展示预测分数、排名变化和解释信息。
8. 用户可保存结果，系统将其写入用户历史记录。

### 4.2.2 结构查询与数据浏览交互图

结构查询与数据浏览流程主要服务于结果解释和数据支撑。用户可以查询药物、蛋白质和复合物，也可以浏览本地数据源摘要。系统优先读取本地 CSV、JSON、PDB/CIF 文件和图片缓存；当本地数据不足时，再调用 PubChem、PDB、UniProt 等外部数据接口。

![图4-3 结构查询与数据浏览交互图](详细设计图/图4-3-结构查询与数据浏览交互图.svg)

交互流程说明：

1. 用户在 Explore 或 Data 页面选择查询类型或数据源类别。
2. 前端提交 CID、SMILES、PDB ID、UniProt ID、Sequence 或数据源名称。
3. 后端查询服务先检索本地缓存和本地结构化数据。
4. 若本地命中，则直接返回结构化信息、图片路径或三维结构数据。
5. 若本地未命中，则调用外部 API 获取补充信息。
6. 后端封装查询结果并返回前端。
7. 前端展示表格、结构图片、三维视图或数据分页结果。

## 4.3 UI 设计

### 4.3.1 页面结构总览

平台前端采用 HTML、CSS 和 JavaScript 实现，整体采用统一导航栏和模块化页面结构。页面主色调以浅蓝科技风为主，首页提供系统简介和核心功能入口，功能页面围绕预测、推荐、查询、数据浏览、教程和用户中心展开。

![图4-4 iDrug UI 页面结构设计图](详细设计图/图4-4-iDrugUI页面结构设计图.svg)

### 4.3.2 首页与功能入口

首页 `home.html` 用于展示平台定位、核心功能入口和技术内容。用户可从首页进入多场景预测、个性化推荐、结构查询、数据浏览、教程和用户中心等页面。首页承担平台导览作用，因此 UI 设计应突出核心入口，避免将过多表单和结果信息堆叠在首页。

### 4.3.3 预测与推荐页面

预测相关页面包括 `prediction_models.html`、`plat_DTI_input.html` 和 `plat_DTI_result.html`。其中，输入页面负责收集任务类型、药物输入、靶点输入和用户画像，结果页面负责展示预测分数、排序结果、推荐原因和保存入口。

设计要点：

1. 输入区应明确区分药物输入、蛋白输入和个性化条件。
2. 任务类型选择应与模型适用场景对应。
3. 结果页应突出排名、分数和解释信息。
4. 保存结果按钮应在用户已登录时可用，未登录时给出提示。

### 4.3.4 查询与数据浏览页面

查询相关页面主要包括 `Function.html`、`data_sources.html` 和部分 Explore 功能区域。用户可查询药物、蛋白质和复合物结构，也可浏览本地结构化数据源。UI 设计上应突出查询类型选择、输入框、查询结果和三维结构展示区域。

设计要点：

1. 药物、蛋白质、复合物查询入口应清晰分组。
2. 查询结果应包含基础信息、数据来源、结构图片和可视化区域。
3. 数据浏览应使用分页或摘要，避免一次性加载大量数据。
4. 外部接口失败时，页面应显示清晰错误提示，不应出现空白结果。

### 4.3.5 用户中心与历史页面

用户相关页面包括 `login.html`、`signUp.html`、`userInfo.html`、`saved_results.html` 和 `saved_result_detail.html`。登录注册页面提供基本身份入口，用户中心展示当前登录用户和最近结果，历史列表和详情页用于查看、复用和删除保存结果。

设计要点：

1. 登录和注册页面应保持表单简洁，错误提示明确。
2. 用户中心应展示当前用户身份和历史记录摘要。
3. 历史详情页应展示输入参数、用户画像、排名结果和保存时间。
4. 删除操作应给出成功或失败反馈，避免误删公开 demo 记录。

### 4.3.6 教程页面

`tutorial.html` 用于展示系统使用流程、主要页面说明和演示截图。教程页面服务于课程展示和新用户引导，应以步骤化方式组织内容，帮助用户理解从输入、预测、查询、推荐到保存结果的完整流程。

## 4.4 数据库设计

### 4.4.1 数据库与数据实体总览

平台采用 MySQL 作为主要业务数据库，同时结合本地 CSV、JSON、PDB/CIF 文件和外部 API 形成混合数据支撑体系。MySQL 主要保存用户信息、PDB URL 映射和疾病推荐药物等业务数据；用户保存的预测结果当前以 JSON 文件形式组织；本地知识库用于结构查询、模型输入映射和个性化推荐。

![图4-5 iDrug 数据库设计 ER 图](详细设计图/图4-5-iDrug数据库设计ER图.svg)

### 4.4.2 主要数据表设计

#### User 表

| 字段 | 类型 | 说明 |
|---|---|---|
| `username` | `CharField(32)` | 用户名，唯一。 |
| `password` | `CharField(128)` | 用户密码字段。 |

设计说明：该表用于平台注册登录和 session 身份识别。后续建议将密码改为哈希存储，并增加创建时间、最后登录时间等字段。

#### PDBURL 表

| 字段 | 类型 | 说明 |
|---|---|---|
| `pdb_id` | `CharField(32)` | PDB 编号，唯一。 |
| `url` | `CharField(256)` | 对应结构资源 URL。 |

设计说明：该表用于保存 PDB ID 与结构资源地址的映射，辅助蛋白质和复合物结构查询。

#### DiseaseRecommendation 表

| 字段 | 类型 | 说明 |
|---|---|---|

| `molecular_weight` | `CharField(20)` | 分子量。 |
| `smiles` | `TextField` | SMILES 字符串。 |
| `disease_type` | `CharField(200)` | 疾病类型。 |
| `age_min` | `IntegerField` | 适用年龄下限，可为空。 |
| `age_max` | `IntegerField` | 适用年龄上限，可为空。 |
| `gender` | `CharField(10)` | 性别约束，默认不限。 |
| `drug_name` | `CharField(200)` | 药物名称。 |
| `priority` | `IntegerField` | 推荐优先级，数值越小优先级越高。 |
| `reason` | `TextField` | 推荐理由。 |
| `price_ref` | `CharField(50)` | 参考价格。 |
| `medicare_cn` | `CharField(50)` | 医保覆盖情况。 |
| `usage_summary` | `TextField` | 使用说明摘要。 |

设计说明：该表用于疾病场景下的药物推荐业务数据，可为个性化推荐和结果解释提供依据。

### 4.4.3 保存结果数据设计

当前项目的保存结果以 JSON 文件方式组织，逻辑上可视为 `SavedRecommendation` 实体。该实体与用户存在一对多关系，一个用户可以保存多条预测或推荐结果。

| 字段 | 说明 |
|---|---|
| `save_id` | 保存记录唯一标识。 |
| `user_name` | 所属用户名。 |
| `created_at` | 保存时间。 |
| `task_type` | 预测或推荐任务类型。 |
| `input_payload` | 用户输入的药物、靶点和任务参数。 |
| `patient_profile` | 个性化推荐时使用的年龄、性别、疾病史、过敏史、医保偏好等信息。 |
| `ranked_results` | 排序后的预测或推荐结果。 |
| `status_summary` | 结果摘要，用于历史列表展示。 |

设计说明：JSON 文件方式便于课程项目快速保存复杂结果结构。若后续系统规模扩大，建议将保存结果迁移为数据库表，并将结果详情拆分为主表和结果项明细表。

### 4.4.4 本地知识库设计

本地知识库由多个 CSV、JSON 和结构资源文件组成，主要包括：

| 数据文件 | 用途 |
|---|---|
| `cid_smiles_map.csv` | CID 与 SMILES 映射，用于药物查询和模型输入组织。 |
| `pdb_protein_map.csv` | PDB 与蛋白质信息映射，用于蛋白查询。 |
| `pdb_complex_map.csv` | 复合物结构映射，用于复合物查询。 |
| `disease_tag_dict.csv` | 疾病标签字典，用于用户画像和推荐解释。 |
| `allergy_tag_dict.csv` | 过敏标签字典，用于风险惩罚。 |
| `drug_personalization_metadata.csv` | 药物个性化元数据，用于疾病匹配、禁忌、医保偏好和推荐理由。 |
| `web/drug_metadata.json` | 药物元数据补充信息。 |
| `pic/` | PDB/CIF、结构图片等展示资源。 |

设计说明：本地知识库用于提升查询速度和离线可用性，同时为个性化推荐提供解释数据。由于部分文件会随数据整理更新，后续应补充字段说明和版本信息。

### 4.4.5 数据库初始化与维护

数据库结构由 Django migrations 管理，初始化时应先配置 MySQL 数据库连接，再执行：

```bash
cd backend
python manage.py migrate
```

维护规则如下：

1. 不在公开仓库中提交数据库密码、API Key 或真实生产连接信息。
2. 数据表变更应通过 Django migration 记录，不建议手工修改表结构后不留痕迹。
3. 本地 CSV 和 JSON 数据更新后，应同步更新字段说明和数据来源说明。
4. 大型数据集和模型权重不直接放入 GitHub，可通过部署环境或课程提交压缩包提供。

## 4.5 小结

本章从类图、交互图、UI 设计和数据库设计四个角度对 iDrug 平台进行了详细设计说明。类图明确了 Django 视图、数据模型、序列化器和服务模块之间的关系；交互图描述了预测推荐、结构查询和数据浏览的运行流程；UI 设计说明了各页面的职责和跳转关系；数据库设计则说明了 MySQL 表、本地知识库、保存结果 JSON 和外部数据源之间的协作方式。通过上述设计，系统能够支撑多场景 DTI 预测、个性化推荐、结构可视化、数据浏览和用户结果管理等核心功能。
