# 五、代码实现

本章结合 iDrug 平台的整理后源码，对系统主要功能的代码实现进行说明。代码实现层面围绕“预测—查询—排序—展示—保存”主线展开：前端页面负责收集药物、蛋白和患者画像等输入；Django 后端负责参数校验、任务分发、模型调用、数据查询和结果持久化；模型服务层根据业务场景调用 HyperAttentionDTI、PSICHIC、DeepDTA 等模型；个性化模块在基础 DTI 预测结果之上进行重排序并生成推荐理由。

## 5.2 核心代码解析

### 5.2.1 多场景预测接口入口

对应文件：`github_submit/iDrug-Software-Development-Course/backend/web/views.py`

多场景预测由 `PredictionModelsRunView` 接收 POST 请求。接口读取 `task_type`、`drug_input`、`protein_input` 三类关键参数，先进行合法性检查，再检查是否存在课程演示用的固定结果。只有在输入有效且没有命中缓存时，才进入真实模型推理流程。

```python
task_type = str(data.get("task_type", "")).strip()
drug_input = str(data.get("drug_input", "")).strip()
protein_input = str(data.get("protein_input", "")).strip()

if task_type not in TASK_CONFIG:
    return Response({"error": "Unsupported task type"}, status=400)
if not drug_input:
    return Response({"error": "Drug input is required"}, status=400)
if not protein_input:
    return Response({"error": "Protein input is required"}, status=400)

demo_result = get_prediction_model_demo_result(task_type, drug_input, protein_input)
if demo_result is not None:
    return Response(demo_result, status=200)

result = run_prediction_task(task_type, drug_input, protein_input)
return Response(result, status=200)
```

该接口的实现特点是入口统一、错误处理集中。前端无需直接关心底层调用的是哪一个模型，只需要传入业务任务类型；后端把任务类型转换为具体模型调用，从而降低前端与模型代码之间的耦合。

### 5.2.2 模型任务分发

对应文件：`github_submit/iDrug-Software-Development-Course/backend/web/prediction_model_services.py`

模型调度函数 `run_prediction_task` 将业务场景映射到具体模型。药物重定位和新靶点筛选均使用 HyperAttentionDTI，但加载不同 checkpoint；新药评价调用 PSICHIC；亲和力预测调用 DeepDTA。

```python
def run_prediction_task(task_type, drug_input, protein_input):
    if task_type == "drug_repositioning":
        return run_hyperattention_task(
            task_type,
            drug_input,
            protein_input,
            HYPERATTENTION_HUMAN_CHECKPOINT,
            "HyperAttentionDTI prediction completed successfully.",
        )
    if task_type == "novel_target_screening":
        return run_hyperattention_task(
            task_type,
            drug_input,
            protein_input,
            HYPERATTENTION_GPCR_CHECKPOINT,
            "HyperAttentionDTI GPCR screening completed successfully.",
        )
    if task_type == "new_drug_evaluation":
        return run_psichic(drug_input, protein_input)
    if task_type == "affinity_prediction":
        return run_deepdta(drug_input, protein_input)
    raise ValueError("Unsupported task type")
```

这种写法使四类业务任务拥有一致的外部接口，同时保留模型侧差异。后续如需新增模型或新增预测场景，只需扩展任务配置和分发逻辑，不必重写前端调用流程。

### 5.2.3 HyperAttentionDTI 推理执行

对应文件：`github_submit/iDrug-Software-Development-Course/backend/web/prediction_model_services.py`

HyperAttentionDTI 的推理流程封装在 `_run_hyperattention_batch` 中。该函数先创建运行时临时目录，再将多行输入规范化为模型所需的 CSV 文件，随后通过子进程启动模型脚本，最后读取预测结果并清理临时文件。

```python
def _run_hyperattention_batch(drug_input, protein_input, checkpoint_name):
    model_dir = MODELS_DIR / "hyperattentionati"
    temp_dir = _make_runtime_temp_dir("hyperattention_")
    try:
        input_csv = temp_dir / "input.csv"
        pred_csv = temp_dir / "pred.csv"
        emb_npy = temp_dir / "emb.npy"
        input_rows = _write_pair_csv(
            input_csv,
            _normalize_multiline_input(protein_input),
            _normalize_multiline_input(drug_input),
            include_sample_id=False,
        )
        command = [
            _resolve_python("hyperattentionati"),
            str((model_dir / "inference.py").resolve()),
            "--model_path",
            str((model_dir / "checkpoints" / checkpoint_name).resolve()),
            "--input_csv",
            str(input_csv.resolve()),
            "--pred_csv",
            str(pred_csv.resolve()),
            "--emb_npy",
            str(emb_npy.resolve()),
            "--batch_size",
            "2",
            "--device",
            "auto",
        ]
        _run_subprocess(command, model_dir)
        output_rows = _read_csv_rows(pred_csv)
        return input_rows, output_rows
    finally:
        shutil.rmtree(temp_dir, ignore_errors=True)
```

该实现有三个关键点：第一，使用 `_resolve_python` 选择模型所属环境，避免不同模型依赖冲突；第二，使用临时目录隔离每次推理的输入和输出文件；第三，在 `finally` 中清理临时文件，避免课程演示和多次测试后产生大量中间数据。

### 5.2.4 PSICHIC 与 DeepDTA 模型调用

对应文件：`github_submit/iDrug-Software-Development-Course/backend/web/prediction_model_services.py`

PSICHIC 与 DeepDTA 的调用方式与 HyperAttentionDTI 类似，均采用“写入输入 CSV、执行模型脚本、读取输出 CSV、构造统一结果”的流程。不同点在于命令行参数、结果字段和模型目录不同。

```python
def run_psichic(drug_input, protein_input):
    model_dir = MODELS_DIR / "psichic"
    temp_dir = _make_runtime_temp_dir("psichic_")
    try:
        input_csv = temp_dir / "input.csv"
        result_dir = temp_dir / "outputs"
        result_dir.mkdir(parents=True, exist_ok=True)
        input_rows = _write_pair_csv(
            input_csv,
            _normalize_multiline_input(protein_input),
            _normalize_multiline_input(drug_input),
            include_sample_id=False,
        )
        command = [
            _resolve_python("psichic"),
            str((model_dir / "inference.py").resolve()),
            "--device",
            "cpu",
            "--classification_task",
            "True",
            "--trained_model_path",
            str((model_dir / "checkpoints").resolve()),
            "--screenfile",
            str(input_csv.resolve()),
            "--result_path",
            str(result_dir.resolve()),
        ]
        _run_subprocess(command, model_dir, env=env)
        output_rows = _read_csv_rows(result_dir / "pred.csv")
    finally:
        shutil.rmtree(temp_dir, ignore_errors=True)
```

通过统一封装，平台能够把多个来源、多个输入格式的模型结果转换为前端可直接展示的 `result_items`。这也使后续系统测试可以围绕统一响应结构编写，而不必分别适配每个模型脚本的原始输出。

### 5.2.5 DTI 个性化推荐接口

个性化推荐接口 `DTI.post` 负责解析用户提交的 PDB ID、PubChem CID 与患者画像字段。系统先把 CID 转换为药物信息和 SMILES，把 PDB ID 转换为蛋白信息和序列，再调用 HyperAttentionDTI 得到基础概率分数。若用户提供了个性化信息，则继续执行药物重排序。

该接口体现了平台的主业务闭环：药物与蛋白信息查询用于补齐模型输入，模型预测用于得到基础 DTI 分数，个性化重排序用于把预测结果转化为更接近患者场景的推荐结果。

### 5.2.6 个性化重排序核心算法

对应文件：`github_submit/iDrug-Software-Development-Course/backend/web/personalization.py`

个性化重排序函数 `rerank_drugs` 首先对基础 DTI 分数进行归一化，然后为每个候选药物匹配临床元数据，分别计算疾病适配分、医保偏好分以及年龄、性别、过敏、禁忌、慎用等风险扣分。最终分数计算完成后，系统按最终分数降序排序，并保留原始 DTI 排名以便对比。

```python
normalized_scores = normalize_dti_scores(raw_scores)
for source_index, drug in enumerate(drug_info_list):
    metadata, matched_by = find_metadata_for_drug(drug)
    disease_score, matched_disease_tags = score_disease(
        patient_profile["disease_history"], metadata
    )
    age_penalty, age_penalty_level = penalty_age(patient_profile["age"], metadata)
    sex_penalty, sex_penalty_level = penalty_sex(patient_profile["sex"], metadata)
    insurance_score, insurance_weight = score_insurance(
        metadata, patient_profile["insurance_preference"]
    )
    allergy_penalty, matched_allergy_tags = penalty_allergy(
        patient_profile["allergy_history"], metadata
    )
    contraindication_penalty, matched_contraindication_tags = penalty_contraindication(
        patient_profile["disease_history"], metadata
    )
    caution_penalty, matched_caution_tags = penalty_caution(
        patient_profile["disease_history"], metadata
    )

    final_score = (
        0.65 * dti_score_norm
        + 0.20 * disease_score
        + insurance_weight * insurance_score
        - age_penalty
        - sex_penalty
        - allergy_penalty
        - contraindication_penalty
        - caution_penalty
    )
    final_score = round(clamp_score(final_score), 6)
```

该算法保留了模型预测在排序中的主要权重，同时加入临床适配和用药风险约束。这样可以避免只根据相互作用概率进行推荐，使输出更符合“辅助推荐”而不是“单纯预测”的产品定位。

### 5.2.7 推荐理由与分数明细生成

对应文件：`github_submit/iDrug-Software-Development-Course/backend/web/personalization.py`

重排序完成后，系统不仅返回最终分数，还返回 `score_breakdown`、`match_info` 和 `recommendation_reason`。这些字段用于前端展示“为什么推荐该药物”，提升系统结果的可解释性。

```python
recommendation_reason = build_recommendation_reason(

    "dti_score_norm": round(clamp_score(dti_score_norm), 6),
    "final_score": final_score,
    "score_breakdown": {
        "s_dti": round(clamp_score(dti_score_norm), 6),

        "s_insurance": round(clamp_score(insurance_score), 6),
        "p_age": round(clamp_score(age_penalty), 6),
        "p_sex": round(clamp_score(sex_penalty), 6),
        "p_allergy": round(clamp_score(allergy_penalty), 6),
        "p_contraindication": round(clamp_score(contraindication_penalty), 6),

```

可解释性字段的设计让平台能够同时展示“原始预测强度”“个性化调整依据”和“最终推荐排序”。在课程项目展示中，这部分能够清楚体现系统从 AI 预测走向应用辅助决策的过程。

### 5.2.8 蛋白与复合物查询实现

对应文件：`github_submit/iDrug-Software-Development-Course/backend/web/protein_services.py`

蛋白和复合物查询模块负责把用户输入的 PDB ID、UniProt ID 或序列信息解析为前端需要的统一结构。实现上优先查询本地数据，若本地不存在则调用在线接口进行补全；当外部接口失败时，返回可展示的降级结果，避免页面中断。

```python
def query_complex_info(query):
    query = str(query or "").strip()
    if not query:
        raise ValueError("Complex query is required")

    local_info = get_local_complex_info(query)
    if local_info:
        return local_info

    online_info = get_online_complex_info(query)
    if online_info:
        return online_info

    return build_fallback_complex_info(query)
```

该模块的核心思想是提高查询功能的稳定性。课程演示时，即使外部数据库网络不稳定，系统也能通过本地缓存或降级结果保持页面可用。

### 5.2.9 推荐结果保存与历史管理

对应文件：`github_submit/iDrug-Software-Development-Course/backend/web/views.py`

推荐结果保存接口从请求体中读取推荐结果 JSON，检查当前 session 用户，生成唯一 `save_id` 后写入用户独立目录。列表、详情和删除接口基于同一目录结构读取文件，并对 demo 记录和非本人记录进行保护。

```python
username = _current_session_username(request)
if not username:
    return JsonResponse({"success": False, "error": "Login required"}, status=401)

save_id = f"{timezone.now().strftime('%Y%m%d%H%M%S')}_{uuid.uuid4().hex[:8]}"
save_path = _user_saved_recommendations_dir(username) / f"{save_id}.json"
save_payload = {
    "save_id": save_id,
    "username": username,
    "created_at": timezone.now().isoformat(),
    "result_payload": result_payload,
}

with save_path.open("w", encoding="utf-8") as fp:
    json.dump(save_payload, fp, ensure_ascii=False, indent=2)

return JsonResponse({"success": True, "save_id": save_id})
```

这种轻量级 JSON 持久化方式适合课程阶段的结果管理需求：实现简单、便于调试、便于查看保存内容，也不会引入过重的数据库迁移成本。若后续进入生产化阶段，可以将该模块迁移到数据库表中，以支持更复杂的检索、分页和权限管理。

### 5.2.10 前后端协同实现

前端页面通过 HTML、CSS 和 JavaScript 组织用户交互，后端则以 Django APIView 的形式提供数据接口。前端提交输入后，后端返回统一 JSON，页面再根据字段渲染预测分数、药物信息、蛋白信息、推荐理由和历史记录。

从实现职责看，前端主要承担以下工作：

1. 收集药物、蛋白、患者画像等输入。
2. 调用后端预测、查询、保存等接口。
3. 对返回结果进行表格、卡片和详情页展示。
4. 对错误信息、空结果、加载状态进行用户提示。

后端主要承担以下工作：

1. 参数校验与异常处理。
2. 模型任务调度与推理结果解析。
3. 药物、蛋白和复合物信息查询。
4. 个性化推荐分数计算与理由生成。
5. 用户登录状态和历史结果文件管理。

## 5.3 小结

iDrug 的代码实现采用了较清晰的分层思路：页面层负责交互，视图层负责接口入口，服务层负责模型和数据逻辑，个性化模块负责推荐算法，保存模块负责用户结果管理。核心代码围绕统一输入、统一调度、统一输出展开，使多个模型和多个业务场景能够在同一平台中协同工作。
